### 1. Give coding models task cards, not a single champion

Topic:
How to evaluate newly released coding models inside an engineering organization.

Hook:

A new coding model does not need to win every benchmark. It needs to earn a place in a task card.

Why now:
GitHub has started rolling out GPT-6.1 Sol in Copilot for agentic coding and terminal workflows, reporting fewer tokens and steps in early testing than earlier GPT-6 and GPT-5.6 models.

Unique angle:
Replace the search for one “best” coding model with a task-specific operating practice that tracks review burden and recurring failure types.

Draft:

A new coding model does not need to win every benchmark.

It needs to earn a place in a task card.

When a new model appears in the IDE, the easy question is: is it better?

The useful question is: better at which work, under which constraints?

I would test it against a small set of tasks we already understand:

1. Fix a failing test without widening the change.
2. Refactor a module while preserving a public contract.
3. Make a multi-file change that crosses a real repository boundary.
4. Investigate a production-like bug with incomplete information.

For each task, measure more than elapsed time.

Was the diff reviewable?

Did it introduce a familiar class of regression?

How many human corrections were needed before merge?

What did the successful fix actually cost?

That gives you a task card, not a leaderboard.

One model may be excellent at constrained fixes. Another may be worth the extra cost for cross-cutting changes. A third may be useful only when the human is already steering closely.

The goal is not to name a champion.

The goal is to route each kind of work to the model that gets it over the line with the least review burden.

### 2. Your developer portal should own the truth, not a copy of it

Topic:
Using GitHub external custom properties without creating a second source of truth.

Hook:

The risk in bringing business context into GitHub is not missing metadata. It is trusting stale metadata.

Why now:
GitHub has introduced external custom properties in public preview so an external system can exclusively own and continuously synchronize repository context such as ownership, service tier, lifecycle stage, and compliance status.

Unique angle:
Treat the integration as a change-control problem: source ownership, freshness expectations, and an observable version for the facts used in governance decisions.

Draft:

The risk in bringing business context into GitHub is not missing metadata.

It is trusting stale metadata.

A repository property can look harmless: owner, service tier, lifecycle stage, compliance status.

But those fields start to matter when they drive a ruleset, an exception, an escalation, or a deployment decision.

If the payment service changed owners yesterday and the repository still says otherwise, the dashboard looks complete while the decision is wrong.

GitHub's new external custom properties are interesting for that reason. The external system can stay the owner while GitHub consumes the context for views, filtering, and governance.

The integration still needs a contract:

1. Which system owns each property?
2. How quickly must updates appear after a change?
3. What happens when the source is unavailable?
4. Can an engineer see the property version behind a governance decision?
5. Who notices a property that has not been refreshed when expected?

Metadata becomes infrastructure the moment a policy depends on it.

At that point, freshness and ownership are not admin details. They are part of the control plane.

### 3. An agent needs a recovery plan before its first tool call

Topic:
Designing multi-step agent workflows for partial failure.

Hook:

The hardest agent failure is not a wrong answer. It is a half-completed workflow with no safe next move.

Why now:
Current enterprise agent discussions are moving from model capability to tool execution across production systems, where a workflow can fail after one external action succeeds and the next one does not.

Unique angle:
Frame agent reliability as an execution-design discipline: idempotency, durable state, compensations, and a human escalation boundary.

Draft:

The hardest agent failure is not a wrong answer.

It is a half-completed workflow with no safe next move.

Imagine an agent that updates a customer record, calls a payment service, and then fails before it can write the final audit event.

“Retry” is not a recovery strategy unless every step was designed for it.

Production agent workflows need a few unglamorous properties:

1. An idempotency key for every operation that can be retried.
2. A durable record of the completed step before the next side effect starts.
3. A compensating action for work that can be reversed.
4. A clear escalation path for work that cannot.
5. A trace that lets an operator reconstruct the state without asking the model to remember it.

This is not a limitation of agents. It is the same discipline that makes distributed backend systems survivable.

The difference is that an agent can choose its next tool call dynamically.

That makes the recovery contract more important, not less.

Before giving an agent authority to act across systems, ask one question:

If it fails after step three, who knows exactly what happened and what the safe next action is?

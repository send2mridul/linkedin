### 1. Automated code review needs a reason to start, not just a button

Topic:
GitHub Copilot code-review API support and review-effort selection.

Hook:

The useful part of GitHub's Copilot code-review API is not the API itself. It is that review effort can now be chosen by the workflow that requests it.

Why now:
GitHub added REST and GraphQL support for requesting Copilot code review on 2 October, with an optional effort level per request.

Unique angle:
Automation can make review intentional instead of applying one default everywhere. A team can define which changes deserve a broader pass based on the trigger, ownership, or risk signal, then still keep the final decision with a reviewer.

Draft:

GitHub's new Copilot code-review API has one detail I like: the workflow can choose the review effort for each request.

That makes it possible to treat automated review as part of delivery policy instead of a button someone remembers to click.

For example, a team could ask for a more thorough pass when a change touches an authentication path or a schema migration, while keeping routine documentation changes lightweight.

The interesting question is not whether an AI review should run on every pull request. It is whether the trigger matches the risk of the change.

### 2. Credentials are API inputs, not strings to pattern-match

Topic:
GitHub's completed rollout of stateless App installation tokens.

Hook:

One GitHub token rollout is a useful reminder that credentials should be opaque values, even when their format has looked stable for years.

Why now:
GitHub completed the rollout of stateless App installation tokens on 2 October. New tokens are roughly 520 characters instead of the legacy 40-character format.

Unique angle:
The change is not only about authentication. It exposes hidden assumptions in database columns, secret stores, header limits, log redaction, and validators that were written around a familiar token shape.

Draft:

GitHub just finished moving App installation tokens to a new stateless format. The permissions and one-hour lifetime stay the same, but the token grew from roughly 40 characters to around 520.

It is a small reminder that credentials should be treated as opaque values.

The dangerous code is usually not the authentication code. It is the validator that expects a fixed length, the secret store with a tight column, the proxy with a header limit, or a redaction rule that only knows the old pattern.

An auth upgrade should not turn into a production incident because a token looked different than it did last year.

Important sources / fact check:

- https://github.blog/changelog/2026-10-02-stateless-github-app-installation-tokens-rolled-out/
- GitHub documents the token-format change, unchanged permissions and expiry, and the fixed-length, storage, proxy, and redaction checks. The operational conclusion is engineering judgment.

### 3. Review tools need to separate the original diff from the fixes made during review

Topic:
px0's unpushed-commit review and pull-request scope features.

Hook:

When an agent helps fix a pull request, the reviewer needs to see two different things: the author's change and the changes made while reviewing it.

Why now:
px0 v0.1.13 added review scopes for the whole pull request, the reviewer's own changes, or a selected range, plus an unpushed-commit view.

Unique angle:
Agent-assisted editing makes the distinction between source changes and review fixes more important. Mixing them into one diff can make it harder to answer the basic review question: what did the author propose, and what did we change in response?

Draft:

One small code-review feature I found interesting is px0's new pull-request scopes: whole PR, my changes, or a selected range.

That sounds like a UI detail, but it matters more when review tools can make edits through an agent.

After a few fixes, one giant diff stops answering a basic question: what did the author change, and what changed during review?

Keeping those views separate makes the review trail easier to reason about. It also makes it safer to use agents for small corrections without losing the original context.

Important sources / fact check:

- https://github.com/px0-ai/px0/releases
- https://px0.ai/docs/guides/github-pr-review
- The v0.1.13 release documents the scopes and unpushed-commit review. The review-process takeaway is engineering judgment.
